Tech Stack Proposal A — The Lantern Reach

A proposed stack for the first vertical slice, The Lantern Reach: a native base engine that changes only with a release, a live scripting layer where the AI game master works, and an optional fast-model layer under it. It follows the locked decisions in the High-Level Plan and the setup in A Fast Layer Under the Game Master. Target: Windows 11, RTX 5070 Ti with 16 GB, i5-14400F, 32 GB of RAM, fully offline. AI coding agents write most of the code. There are no time estimates on this page.

The recommendation, one line per layer

Recommendation Rust base engine, Luau scripting layer, llama.cpp sidecar for fast models.

The base engine is a headless-first Rust simulation with a thin 2D renderer on top. The game master, and the authored backbone too, live in sandboxed, strictly typed Luau packs that run on events and write only through a command buffer. Nothing applies until the change has passed a forked headless run, and every write carries its cause, so the change can be undone in-world. Fast models pick from menus the scripts define, and utility AI always answers first. One binary exposes a JSON CLI that agents, tests and the game master all use.

Base engine

Rust, with wgpu, winit, kira and SQLite. A deterministic fixed-step simulation library that runs without a window, plus a small sketch-style 2D renderer and one galaxy binary with a JSON CLI.

Scripting layer

Luau in strict mode, hosted through mlua. Packs of scripts, data and assets that are sandboxed, budgeted and event-driven. Each change is validated in a forked headless run, applied at a calm moment and rolled back by cause.

Fast-model layer

A bundled llama-server (CUDA build) running Qwen3.5-4B at Q4_K_M, called by a Rust decision service. Utility AI answers first. The model only picks from menus the scripts define, under a JSON schema, and off is a complete game.

The stack at a glance

  1. AI game master (outside the game)

    Claude Code, Codex or another agent. It reads digests and proposes packs through the galaxy gm CLI and never touches memory or files the game owns.

  2. proposes a pack and gets a validation report back
  3. Scripting layer (live)

    Luau packs: the authored backbone (core) plus a per-save game master pack (gm). Beats, factions, traits, market tables, NPC briefs, line pools, station stages and fast-model menus.

  4. calls the declared hooks only; writes go to a command buffer with a cause
  5. Base engine (release only, Rust)

    Sim kernel, stores with stable IDs, history log, event bus, verbs, flight, pricing, saves, script host, validator, snapshots, renderer, audio, CLI and the decision service.

  6. asks for a typed choice inside a budget, and utility AI answers if the model is late
  7. Fast-model sidecar (optional)

    llama-server.exe on a free localhost port with a GGUF model. Started and stopped by the engine.

The base engine

The engine is an explicit experiment in a custom engine, so it should be small and shaped exactly like this game: a top-down 2D world with a few hundred rocks and ships, six stations and a deep world state. The hard parts are not rendering. They are determinism, stable IDs, a history log and the ability to fork a save and fast-forward it. The stack is chosen for those.

Four rules the engine is built around

  1. 1
    Headless first.

    The sim crates have no dependency on the window, the GPU or audio. The game executable is a renderer and input layer wrapped around the same library that galaxy sim runs at thousands of ticks per second.

  2. 2
    Stable IDs everywhere.

    Authored things have namespaced string IDs such as station.kettle_dock. Live-created things get IDs from their pack, such as gm.sixth_station.station. IDs are interned to integers at runtime. Saves, scripts, history facts and fast-model packets all speak these IDs, which is what Proto 6 showed lets progress survive a reload.

  3. 3
    One write path.

    Every change to world state, whether from a verb, a script or a fast-model choice, is a typed command with a cause. The engine applies commands at the end of a tick, checks runtime invariants and appends the matching history facts. That gives scripts transactions, and gives rollback something to undo.

  4. 4
    Same verbs for everyone.

    The player ship, the automated craft, scripted NPC craft and the test bot all issue the same verbs: fly, mine, dock, buy, sell, wait and loop. Control tiers only change how the player produces verbs, never what verbs do.

What the engine deliberately does not have

  • No editor. Content is text in packs, and the dev harness jumps to any beat.
  • No native plugins, no DLL loading and no Rust hot reload. A base change means a new build and a restart, which matches the locked hot-reload tiers.
  • No real-time clock, timer or countdown API available to scripts. Pacing uses activity counters only, so the "no timers" invariant holds by construction.
  • No networking beyond localhost: the CLI pipe and the optional llama-server port. Optional OpenRouter access stays out of the slice unless Andreas opts in.

The scripting layer

Why Luau

Luau is Roblox's typed descendant of Lua 5.1. It was built to run untrusted code from millions of authors, which is close to the game master's situation.

  • +A sandbox by design. No file, process or network access in the language. Globals can be frozen with sandbox mode, and the VM supports interrupt callbacks for instruction budgets and per-state memory limits.
  • +Gradual static types. --!strict scripts are checked against a definitions file generated from the contract crate, so "the script only touches declared hooks" is a type error before anything runs.
  • +Agents know it. Lua and Roblox Luau are a very large body of public code, and the syntax is small.
  • +Instant reload. No compile step. A pack reload is parse plus typecheck plus load.
  • −Costs. Typechecking needs the Luau analyzer binary pinned alongside the game. Floating-point maths in scripts is deterministic only on the same build, which is enough for this slice.

Packs

A pack is a folder with a manifest.toml, Luau scripts, TOML data (market tables, factions, briefs, line pools, canon nodes) and optional assets. The slice runs two pack layers:

core: the authored backbone

All 17 beats, three factions, pilot traits, Tandem and Heron abilities, market tables, about 10 named NPCs and their line pools. Shipped with the slice and written by coding agents through the same API the game master uses.

gm: the live layer, per save

Everything the game master adds or changes. It lives inside the save file as revisions addressed by content hash, so a save carries its own history of changes.

Writing the backbone through the game master's API is the main design bet. If the authored journey can be built through the 14 hooks, the game master can build on them too. Any time the backbone needs something the hooks can't do, that goes on the "needed a base change" list, which answers the slice's question 7 directly.

What a script looks like

Change type 1, growing Kettle Dock from deliveries:

--!strict
local G = require("@galaxy")

return G.script {
  id = "gm.kettle_growth",
  uses = { "events.dock", "history.read", "stations.write",
           "market.levers", "assets.kit", "talk.write" },

  on = {
    dock = function(ev: G.DockEvent, ctx: G.Ctx)
      if ev.station ~= "station.kettle_dock" then return end
      local ice = ctx.history:count { kind = "deliver", station = ev.station, ware = "ware.ice" }
      local st = ctx.stations:get(ev.station)
      if ice >= 20 and st.stage < 2 then
        local why = ctx:cause { summary = "greenhouse stage 2 from the player's ice", facts = ice.ids }
        ctx.stations:set_stage(ev.station, 2, why)
        ctx.kit:attach(ev.station, "part.greenhouse_dome_b", why)
        ctx.market:add_producer(ev.station, "ware.rations", 0.5, why)
        ctx.talk:offer { person = "npc.ilse", place = ev.station, cites = why,
                         line = "Kettle's second dome is up. That was your ice." }
      end
    end,
  },
}

The script never holds world state in Lua variables. It reads through ctx, writes commands with a cause, and anything it must remember goes into a typed per-script store declared in the manifest and saved with the world. That is why a reload loses nothing.

Sandboxing

ThreatGuard
Reaching outside the gameLuau has no io or os.execute. require is replaced with a loader that only sees @galaxy and the pack's own modules. os.time, os.clock and math.random are removed; randomness comes from ctx.rng, seeded per script and event.
Touching undeclared stateStatic: strict typecheck against the generated definitions. Dynamic: ctx is built from the manifest's uses list, so undeclared namespaces are simply absent at runtime.
Infinite loops and slow handlersA VM interrupt counts instructions per handler call. Over budget, the handler is aborted and its commands are discarded. Repeated aborts quarantine the script and record a history fact.
Memory blow-upOne Luau state per pack with a memory limit. Query results from history and the stores are capped and paginated.
Half-applied changesHandlers write to a command buffer. On error, nothing applies. On success, the whole buffer applies atomically at the end of the tick.
Breaking design rules at runtimeThe command applier checks runtime invariants: no destroyed or devalued player property, no write to a seen place without a legibility line citing a fact, and prices inside the bands the market allows.
Bad assetsAssets are decoded by the engine's own PNG and SVG loaders with size limits, and referenced by ID from the manifest. No shaders or code ride along with assets.
Damaging the live game during validationSandbox runs happen in a separate galaxy sim child process on a forked copy of the save, so a runaway script can only hurt the copy.

Scripts never run per frame. They run on events, on activity-counter thresholds and on the "calm moment" signal (docked or paused). Flight, mining and pricing maths stay native. That keeps frame time safe and makes the script budget easy to reason about.

Hot reload

There are two paths into a running game, and both go through the same loader and validator.

Dev reload, for coding agents

In a dev build, a file watcher on packs/ reloads a changed pack after the fast checks (types, schema, canon, static invariants). The full sandbox run is skipped unless --sandbox is passed. If a check fails, the last good revision keeps running and the report appears in the overlay and on the CLI, which is Proto 6's behavior.

Live change, for the game master

galaxy gm propose ./change sends a pack revision over a local named pipe. It is validated in full, staged with a snapshot, and applied at the next calm moment. There is no in-game approval inbox; the player meets the change in the world.

A reload swaps the pack's Luau state and re-registers its handlers between ticks. Persistent script data lives in engine stores, so nothing is lost. If no game is running, the same CLI works on the save file, applying on next load. That covers both answers to the open question about how the game master runs during play.

Validation

This is the slice's cut-down pipeline from the vertical slice page, made concrete. Every step writes into one JSON validation report whose format is part of the frozen contract.

  1. 1
    Types and schema.

    Strict Luau typecheck against galaxy.d.luau. TOML data checked against the generated JSON Schemas. Every hook used must be declared in uses, and every ID referenced must exist or be created by this pack.

  2. 2
    Canon check.

    Every Ancients claim cites a node in the canon graph (canon.toml). Locked nodes beyond the open chapter can't be revealed, and line text is scanned for forbidden canon terms.

  3. 3
    Invariants.

    Some hold by construction, such as no clock API, which means no timers. The manifest declares shocks and the opportunities paired with them, and the validator checks the pairing. The others (no level scaling, no destroyed player property) are checked dynamically in step 4.

  4. 4
    Sandbox run.

    Fork the current save into a child process. Fast-forward a fixed amount of activity (dockings, deliveries, jumps) with the journey bot playing, once with the change and once without. Compare telemetry: prices inside bands, no runaway producers, no beat that can no longer resolve, no runtime invariant hits, no handler over budget.

  5. 5
    Legibility check.

    Every write to a place the player has seen must pair with a talk line, map note or chronicle entry that names a place and a person and cites a history fact ID. During the sandbox run, the validator confirms those lines actually fire.

  6. 6
    Snapshot, then stage.

    Write a snapshot row into the save, stage the revision, and apply it at the next calm moment. The report returns accepted, rejected with reasons and locations, or applied with a change ID.

W5's deliberately bad script, the one that must be rejected, becomes a permanent test. The other steps from The Game Master's Menu (charter, exploit scan, novelty fingerprint) can be added later as more steps in the same report without changing the API.

Rollback

Because every command carries a cause, the engine knows exactly which writes a change made, so rollback works at two levels.

In-world rollback (default)

galaxy gm rollback <change-id> computes the inverse of every write caused by that change and applies it as a new change with its own legibility line, such as Ilse saying the depot handover fell through. Things the player earned stay earned. The pack revision is deactivated. Automatic triggers: repeated handler aborts, runtime invariant hits or a telemetry alarm such as a runaway price.

Hard restore (fallback)

Load the snapshot taken before the change and the previous pack set. It is exact, but it loses play since the snapshot, so it is a developer and harness tool, not the game master's normal path.

Some commands are not cleanly reversible, for example a rumor the player has already heard. The contract marks each command as reversible or compensate-only, and the validator warns when a change leans on the second kind.

The boundary and the API surface

Rule Native code owns how things work. Scripts own what exists, when, and why.

Anything per-frame, numeric at scale or safety-critical is native: flight, mining, pricing maths, verb execution, saves, invariants and validation. Anything that is content, pacing, rules of a place or a person, or a reason to change is script: beats, factions' behavior, traits, market tables, station stages, briefs, menus and lines. Scripts compose; the engine executes.

Expected to need a base change

These are listed up front so question 7 starts with an honest list. Each would be a new release, not a script:

  • A truly new primitive verb, such as rock tagging if it can't be built from mine, wait and flags. Composite verbs are scripts; new physics is not.
  • A new kind of UI screen. Scripts can fill reserved slots and panels with declared widgets, but can't invent layouts.
  • New pricing maths. Levers can change inputs, not the formula.
  • Any new hook. That is a contract change.

How the fast-model layer plugs in

It follows the research page's recommended starting setup, split along the same boundary: the engine owns the plumbing and the safety, and scripts own what NPCs may do and how they talk.

  1. Something happens near the player

    Docking, a jump, a shortage threshold or a passing trader. Requests come from events, never from a per-tick clock.

  2. the engine builds a grounding packet: the brief, state with IDs, and recent facts
  3. Utility AI scores the menu (native, always on)

    The curves and the menu come from the script pack. The top choice is already a complete answer and is held as the default.

  4. if a model is enabled, within budget and the GPU has headroom
  5. llama-server picks

    The top three or four options plus temperament go to the model. Output is constrained by a JSON schema built from the menu: an action ID from an enum plus typed fields, and a length-capped line if the menu item allows text.

  6. within a deadline; otherwise the default stands
  7. Validator (native)

    The six checks from the research page: shape, references, rules, limits, text, and on failure the utility choice plus an authored line. It never retries in a loop.

  8. the result applies as an ordinary command with cause mind:<brief>@<rev>
  9. History and the game master's digest

    The outcome is a fact like any other. Dock talk can cite it, rumors can spread it, and the game master reads it.

In the base engine (crates/mind)

  • Starts llama-server.exe on a free localhost port at below-normal process priority, checks its health, and stops it on exit.
  • A request queue on a worker thread. The frame thread never waits.
  • The fallback chain: local model, then cloud if opted in, then utility AI.
  • A situation cache keyed by the brief revision, fact IDs and the menu.
  • The validator, budget accounting and write-back.

In script packs (ctx.mind)

  • NPC briefs: goals, temperament, allowed actions, limits, knowledge, voice and off-limits topics.
  • Menus for traders' routes, dock talk, rumor spread and shortage reactions.
  • Utility curves and authored fallback line pools.
  • Per-region call budgets, set by the game master.

Determinism and tests

Model answers are not deterministic, so every model decision is recorded as a fact with its request key. Replays and sandbox runs read recorded decisions where they exist and use utility AI otherwise. Headless tests run with --mind off by default, which also proves that off is a complete game. A separate galaxy mind bench command measures latency and frame cost with the real model on this card.

Why agents can work well in this stack

Agents do best with fast, honest feedback they can read as text. Every part of this stack gives some.

  1. 1
    The compiler is the first reviewer.

    Rust's type system, the borrow checker and Clippy reject most agent mistakes before a test runs. The contract crate means a workstream that drifts from the shared interfaces fails to build, not to integrate.

  2. 2
    Crate boundaries match workstream ownership.

    Each of W1 to W6 owns its crates (see the layout). Agents touch their own folder plus contract change requests, so parallel work rarely conflicts.

  3. 3
    Headless simulation is the default.

    The sim crates build and test without a GPU. cargo test needs no window, and galaxy sim fast-forwards a save far faster than real time.

  4. 4
    Determinism makes tests exact.

    Golden replays record an input or verb stream and assert world-state hashes at checkpoints. A diff names the first tick and the first store that diverged.

  5. 5
    The journey bot is the shared test.

    The bot plays all 17 beats by issuing the same verbs as the player, with goals read from the backbone beats. If a beat can't be finished, the bot report names the beat and the missing precondition.

  6. 6
    Agents can see the game.

    galaxy shot renders any save or beat offscreen to a PNG, so an agent can look at art and UI changes without a window or a person.

  7. 7
    Content agents never wait for a compile.

    Luau packs reload live in a dev build, and galaxy pack check gives the same JSON report the game master gets.

  8. 8
    Checks run locally.

    cargo xtask check runs fmt, Clippy, the tests, the pack checks, the golden replays and the bot run. Validation stays on the PC, with no CI workflows.

Two alternative stacks and why they lost

Alternative 1: C++20, SDL3 and LuaJIT

The classic custom-engine stack: SDL3 for windowing, input, audio and its GPU API, LuaJIT through sol2 for scripting, and SQLite for saves.

  • +The most-documented way to build a game engine, and LuaJIT is very fast.
  • +SDL3 covers a lot of platform code in one library.
  • −Memory and undefined-behavior bugs from agent-written C++ show up late, as crashes during play rather than compile errors.
  • −CMake and dependency management are a constant tax on agents.
  • −LuaJIT has no static types, and its FFI makes the sandbox easy to break. The game master's scripts would be checked only at runtime.

Why it lost: the two things this project most needs from a stack are safety for agent-written native code and typechecked, sandboxed game master scripts. It is weaker at both.

Alternative 2: Rust with WebAssembly scripts (Wasmtime)

The same Rust base engine, but the scripting layer is WebAssembly components run by Wasmtime, authored in Rust or AssemblyScript against a WIT interface.

  • +The strongest sandbox available: memory isolation, fuel metering and capability imports.
  • +The WIT interface is a precise, versioned contract.
  • −Every live change needs a compile toolchain. The game master writes Rust, compiles to Wasm and ships binaries, so the review surface is a blob rather than readable source.
  • −The reload loop is slower and heavier for content agents.
  • −Content such as beats, briefs and lines is awkward in a compiled language.

Why it lost, narrowly: the slice's scripts are mostly content and small rules, where readable, instantly reloadable source matters more than the last bit of isolation. If the Luau sandbox fails prototype 1, this is the fallback, and the contract crate makes the swap contained.

Also ruled out early

  • Godot or Unity: not a custom engine, which breaks the locked experiment. Their scripting languages also have no sandbox, so the base and script layers would blur.
  • C# with Roslyn scripts: agent-friendly, but live-loaded .NET assemblies are code injection with no security boundary, which breaks the "no DLL injection" agreement.
  • Tauri, Electron or the browser: the plan already rejects a webview as the long-term home for a flyable game.

Risks and the first three prototypes

Risks

RiskWhy it mattersMitigation
The boundary is drawn wrongToo narrow and every game master idea needs a release. Too wide and scripts become a second engine.The backbone is written through the same 14 hooks. Every "needed a base change" is logged and reviewed at each gate.
In-world rollback gets tangledLater writes can depend on a change being undone.Writes tagged by cause, commands marked reversible or compensate-only, and hard restore as the fallback.
Determinism driftsSandbox comparisons and golden replays become noise.Ordered maps, seeded random generators, no clock in the sim, and a replay-hash test on every xtask check.
Luau tooling integrationThe strict typecheck needs the external analyzer binary and a generated definitions file to agree with mlua's runtime.Prototype 1 proves it first. The analyzer version is pinned next to the game.
The renderer eats the effortCustom engines tend to grow tooling before feel.Sprites, ink lines, text and a few widgets only. No editor. Feel is judged at Gate 1 with placeholder art.
GPU contention with the modelHitches would break the calm.A small model, calls batched at calm moments, a frame-time guard that drops to utility AI, and measuring with galaxy mind bench.
Contract churn across six agentsIntegration gets messy, as the slice page warns.One contract crate, generated artifacts, change requests through W1, and stubs that stay runnable at every merge.
Rust build times slow iterationAgents loop on compile.Many small crates, incremental dev builds, optimized dependencies in the dev profile, and content work in Luau with no compile at all.
Model licensesBundling must be allowed.Start with Apache-2.0 models (Qwen3.5-4B, Gemma 4 E4B), as the research page advises.

The first three things to prototype

  1. 1
    The script host end to end.

    mlua with Luau inside a minimal world store: the sandbox, an instruction budget, a memory cap, the command buffer with causes, a generated galaxy.d.luau passing a strict typecheck, dev hot reload, and in-world rollback by cause. Run it on the Kettle Dock growth script and on one deliberately bad script.

    Pass The good script grows the station and survives a reload with its state. The bad script is rejected with a precise report. An infinite loop is cut off without a hitch. Rollback restores the station with a line that cites the cause.

  2. 2
    Fork and fast-forward headless.

    The sim core with SQLite saves and a crude bot issuing verbs. galaxy sim run forks a save into a child process, fast-forwards by activity, and emits telemetry and a state hash as JSON.

    Pass Two runs from the same save give identical hashes. A fork never touches the live save. The run is fast enough that a sandbox check fits between the player docking and undocking.

  3. 3
    The Wren in a window, with the model running.

    The wgpu sketch renderer, WASD flight that stops on release, Space to mine one rock and dock at one ring, and the PAUSED card, while llama-server with Qwen3.5-4B answers dock-talk menus in the background.

    Pass Flight feels right to Andreas with placeholder art. Frame pacing stays steady while the model answers. A dock decision lands in under a second, and with --mind off nothing changes but the words.

Together these three answer the riskiest parts of the stack: the sandbox and boundary, validation by forking, and feel next to the GPU model. They come before any contract is frozen.
