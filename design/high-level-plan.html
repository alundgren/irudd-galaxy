Takeaway

Vision Plan the fun loop first; document lightly and keep it alive.

Modern studios treat the GDD as a living compass—not a 100-page bible—and gate full production on a proven core loop (prototype / MVP) then a vertical slice. For this solo endless trader/miner, that means lock pillars and non-goals, prove mine → haul → sell → upgrade → automate is satisfying with placeholders, then expand systems and optional AI GM content—not code the whole universe first. Saves follow the same rule: local-only for v1; live multi-machine sync later.

How games are normally planned

Industry planning has shifted from waterfall design bibles to agile, living docs plus staged proof that the game is fun and producible.

Artifacts studios actually use

Vision

  • • Vision / one-pager: pitch, audience, pillars, and explicit non-goals.
  • • Living GDD or wiki: short overview plus modular feature pages updated as the game changes (not a frozen tome).
  • • Core loop / MDA notes: Mechanics → Dynamics → Aesthetics so you design from the intended feeling backward.
  • • Prototypes and vertical slice: disposable playables to find fun; then a representative polished path that proves art, UI, audio, and pipeline together before full production.
  • • Production backlog: tickets linked to design intent; scope cuts written down.

Concept locks direction. Pre-production answers whether it is fun and whether you can make it. Production scales only what the slice proved. Polish is feel and finish—not new pillars.

Frameworks that keep design honest

Framework MDA (Hunicke et al.)

What it forces
Start from Aesthetics (feel), then Dynamics, then Mechanics
Use here
Target: discovery, autonomy, slow mastery—not combat thrill

Framework Schell lenses / elemental tetrad

What it forces
Ask hard questions; balance Mechanics, Story, Aesthetics, Technology
Use here
Story optional and pressure-free; tech serves portable saves

Framework Design pillars + non-goals

What it forces
2–4 must-true statements and a written OUT list
Use here
No PvP, no time pressure, combat not the focus

Framework Vertical slice (e.g. Volition / GDC)

What it forces
Gate full production on a representative high-quality path
Use here
One system (mining→trade) at near-shippable quality

Indie vs AAA documentation

AAA often uses a master overview plus owned feature wiki pages, UX briefs, balance sheets, and QA specs. Solo/small indie wins with a one-page living GDD: pitch, core loop, OUT list, art refs, platforms—updated the day scope changes. Over-documenting before a playable loop is a common failure mode.

“We embrace documentation, but not hundreds of pages of never-maintained and rarely-used tomes.”

— Jim Highsmith, Agile Manifesto (via modern GDD practice)

Common planning pitfalls

Rejected

  • − Feature creep: stacking good ideas until nothing ships.
  • − Building systems before the fun loop (economy, AI, narrative tooling with no playable mine→sell cycle).
  • − Static 50–500 page GDDs that rot and mislead.
  • − Skipping the prototype and jumping to full production or a pretty vertical slice too early.
  • − Treating story/content volume as the product before the toy is fun.

What good planning looks like for a solo sandbox trader

For one developer building an endless X3/Elite/EVE-inspired trader without PvP or combat focus, planning is a filter—not a novel.

1
Write pillars and OUT list firstEvery new idea must strengthen the core loop or wait on a later list.
2
Prototype the 30-second–to-session loop with placeholdersMine or buy → move cargo → sell at a better price → upgrade ship/tools → optionally automate one step.
3
Only then add one adjacent system at a timeBases, routes, discovery, quest hooks—each must make the proven loop richer, not replace it.
4
Treat AI (OpenRouter / MCP / Grok Bot GM) as content and tooling, not the core toyProcedural markets, quest text, and GM suggestions after the economy loop works offline.
5
Keep the living Page (this document) currentUpdate the same day you cut or add scope; version with the project.

Design notes

VisionLockedPrototypeEngineRejected

Vision Elevator pitch

A calm, endless space sandbox where you start as a small miner/trader and slowly build automation, bases, and trade routes—with optional discovery and story, never pressure.

Vision Core loop (v1)

Scan/choose a job → extract or buy commodity → haul → sell for margin → reinvest in capacity/automation → repeat with less busywork over time.

Locked Pacing (locked)

About 1 hour a day, thousands of hours of runway. First meaningful automation around 10 hours in—not a 30-minute stamp. Regular upgrades along the way; paper toys that unlock automation in half an hour are too fast.

Vision Progression feel

Incremental number-go-up + RPG talent depth (not stock-market stat spam) + X4 trade/automation. Bigger/more complex tree, fewer ranks per talent, meaningful choices. Soften visible number-optimisation; prefer abilities and qualitative benefits over calc charts.

Prototype Prestige / hull track (Proto 3 starting direction)

Accepted Draft 2: branching hull lineage (Wren then Tandem or Heron, then Mammoth/Firefly/Oracle). At station, P opens prestige/hullwright. World, credits, standing, depletion persist; hull ranks reset with a fee (no refund). Reframe as RPG calling + abilities, not paying to lose work. Draft 1 tree rejected as messy/stock-market. Launch: launch-draft-2.cmd under prototype-3-prestige\.

Vision Quests / horizon

Mass Effect slow arcs blended with No Man's Sky curiosity: world events in space and at stations, exploration rewards, long burn story, plus an infinite world-building thread (e.g. uncovering the Ancients).

Vision Inspiration (feel, not clones)

X3 / X4 economy and ownership; Elite Dangerous exploration tone; EVE industry depth—without PvP or time pressure.

Locked Presentation (locked)

Top-down + Star Traders sketched/cartoony warmth (Proto 1; Proto 4 rejected gray/blue chrome). Soft illustrated industry, not hard metal X4 density. Text is either important or not there — no filler flavor paragraphs; mood via art/animation/sound. Flight is NOT Endless Sky inertia — see Flight model.

Locked Flight model (locked from Proto 1 + Proto 4)

Reject inertia/rocket coasting. Prefer click-to-fly + direct arcade local WASD (stops on release). Controls ARE progression: first ship is Tier0 manual only (steering + Space; no Fly To / world-click travel / queues / loops). Unlock short click → click-mine → click-dock → longer/map click → queues → loop routes → Factorio-ward. Same order verbs for player and future automated ships.

Locked Pause (locked from Proto 6)

A real pause is a core feature: the player can stop the world at any time and resume on their terms. Fits the calm, no-timers design. Liked in Proto 6 (the edit-pause with a clear PAUSED card).

Prototype First automation (Proto 7 — useful direction, form not locked)

A gated, late automation node that works while you are elsewhere is a good first step. The Pip drone itself is not the final form. Open: does the unlock feel like a new game opening or a checkbox; is a drone redundant once your own ship can loop (maybe drone before loops, or give it something the ship can't do); is re-tagging dry rocks a nice check-in or a chore; gate pacing is untimed; tone down numeric Mk tiers per Proto 3. Launch: play.cmd under prototype-7-late-automation\ (--skip or F9 jumps to the gate).

Rejected Audio (needs its own pass)

The synthesized mining-beam and engine loops inherited from Proto 1 are rejected as super annoying. Do not reuse them; audio gets a separate pass across prototypes.

Prototype Trade / living prices (Proto 4 — weaker signal, keep direction)

Chase a price gap yourself before fleets. Living prices react to trades; saturation punishes blind full-load loops. Remote prices must be scouted (aged snapshots), not shown at home dock — discovery feeds later pilot/ship info reach. No on-rails profit guidance. Market UI TBD (future AI-customized views); do not freeze Proto 4 notebook chrome. Launch: PLAY.cmd under prototype-4-two-station-trade\.

Prototype World events / agent content (Proto 5)

Proven: agent-made world changes can be validated, paced and rolled back while the world just evolves. (Proto 5 used JSON cards only as a test format; cards are not a core assumption.) No player approval inbox, no in-UI feedback buttons (fourth-wall talk happens with your own agent outside the game). No timers anywhere, ever: no countdowns, progress bars or days-left; time of day in words. Canon locks guard Ancients reveals. The hard problem is content, not plumbing: avoid the level-scaling trap (same wolf, bigger HP). Content must react to player history and world state. Research quest/world-event systems before building more.

Vision Content design (from the quest and world-event research)

Core rule: variety stored in flavor text runs out, but variety stored in world state does not. Goal: a good game with interesting things to do; the content format is open (storylets/cards are one possible technique, not locked). Principles: the most specific, history-aware content beats generic content, and the world remembers what happened. Changes are lasting and visible, and the player meets them again. Characters recur and remember. The Ancients work as knowledge-as-progression: history generated as structured events first, prose second. A pacing director counts player activity, never clock time. Long community and relationship arcs pay off when the player docks. A human-written backbone of fixed beats has the game master improvising between them (through the scripting engine). Avoid level scaling, Radiant-style template quests, invisible simulation, job boards as the main content, and danger that scales with wealth. Take the Nemesis idea, not its patented implementation. Broader menu of what the game master could do (32 items, base-engine hooks, 9-step script validation pipeline, ready-made prompts): The Game Master's Menu.

Engine Engine (experiment)

Custom engine as a fun experiment. Proto 6 proved validated live data reload (bad data rejected, last good revision keeps running, progress survives via stable IDs). Direction (from Proto 6): agents get a full scripting/modding layer that can inject data, game logic and new assets, not just data. Still no DLL injection or unvalidated edits. Key open design question: where the line sits between the immutable engine (changes only via a release) and the agent-mutable layer. Parallel to the playable loop, not a blocker. Two engines: (1) a base engine that only changes with a new release, and (2) a live-updatable scripting engine on top that can touch most of the game (logic, systems, economy, content, assets). The game master works in the scripting engine. Event cards (Proto 5) are only one small thing it can produce, not the agent interface.

Locked Agent role (locked)

Game master, not virtual players: works through the live scripting engine, which can change most of the game (systems, logic, economy, quests, events, assets). They do not real-time drive NPCs or act as extra captains. The base engine validates script changes and rolls back bad ones.

Open Player growth (open direction)

The pilot can also evolve: a talent or skill set that grows over time alongside the world. It must be much slower and less impactful than ship and world progression, or be tied to a prestige track that resets it. Connects to the Proto 3 RPG tree (few, meaningful choices; no stat spam).

Open Factions (open direction)

Factions are on the table: groups with territory, needs, memory of the player and relationships with each other, which the game master can reshape over time. No combat focus, no PvP.

Open Fast-model layer (open direction)

Two AI layers: the slow, strong game master owns the big picture (arcs, new systems, eras, Ancients canon), while fast, cheap models (small local LLMs or decision models, OpenRouter as an option) make the world feel alive moment to moment (NPC captains, dock chatter, station reactions, rumors, pirate and trader decisions) inside rules and budgets the game master sets. Leanings: fast models pick from what world state allows rather than invent facts; their outcomes are written back to world history for the game master; offline-first, so a small local model on the PC could carry this layer. Research (A Fast Layer Under the Game Master): the game master writes each NPC's brief and budgets; rule-based utility AI always answers first so the game is complete offline; a local Qwen3.5-4B via llama.cpp with schema-constrained output adds personality; OpenRouter (incl. TypeSafe Jev, a cloud decision-only model) is opt-in. Open: frame-rate cost, sameness, canon drift.

Recommended process for this project

Do not start a full prototype codebase until the decisions in Open decisions are answered enough to pick a stack. When coding starts, follow this order.

1
Concept lock (now)Freeze pillars, OUT list, core loop wording, and success criteria for a session that feels worth continuing. Update this Page; no engine commitment required yet.
2
Paper / spreadsheet toyModel one local market: ore yields, haul time/cost, prices, upgrade costs. Validate that automation feels like relief, not a solved game. Hours, not weeks.
3
Disposable core-loop prototypePlaceholder art. One ship, one resource, two stations, buy/sell, simple travel. Local saves only. Kill or rewrite freely.
4
Vertical slice (personal v1 gate)One polished path: mine → haul → sell → buy one automation upgrade, with real UI, local save/load on one computer, and readable feedback. Proves pipeline + feel before bases/quests/AI/sync.
5
Systems expansionAdd one system at a time: multi-commodity markets, route bookmarks, a first base/module, discovery hooks. Each addition must strengthen the proven loop.
6
AI GM and content layerWire optional OpenRouter / MCP / Grok Bot for quest text, rumors, procedural opportunities—offline-safe fallbacks so the game never depends on an API.
7
Live sync (post-v1)Shared store on the Linux VM over VPN (likely SQLite or Postgres). Clients swap freely; save schema designed in v1 so this is a layer, not a rewrite.
8
Polish and personal shipFeel, UX, save reliability, performance. Ship a build Andreas will play for weeks; backlog the rest explicitly.

Suggested v1 scope vs out of scope

v1 is for Andreas only: enough to live in the fantasy on one computer. Everything else waits on a dated backlog.

Locked In scope for personal v1

  • + Single-player, offline-first sandbox
  • + Mining + hauling + trading between a handful of stations
  • + Ship upgrades and one automation path (e.g. auto-mine or auto-haul)
  • + Local save/load on one computer only (no sync)
  • + Light discovery (anomalies, rumors) without mandatory quests
  • + Top-down sketched/cartoon art (Star Traders warmth) + click-to-fly / arcade local control—placeholders fine if the style reads early

Rejected Explicitly out (until cut-in)

  • − PvP, MMO, always-online servers
  • − Seasonal timers, energy, or FOMO loops
  • − Combat as primary progression
  • − Full X4-scale universe and faction simulation on day one
  • − Multiplayer, Steam achievements, marketing polish
  • − Mandatory story that blocks free play
  • − Live multi-machine sync or a shared database in v1
  • − Deep tech that blocks the paper toy / core loop (custom engine is an intentional experiment—keep it parallel, not a gate)

Platform and saves

Machines: MacBook, gaming PC, and a persistent Linux VM on the same VPN. Long-term goal: live sync so Andreas can swap clients without hand-managing saves—likely a small always-on database on the Linux VM. Confirmed for v1: one computer, local saves only. Design the save schema so a later sync layer can sit on top without a rewrite.

Agent review consensus (2026-10-27)

Dual review via T3 Code on the gaming PC: Opus 5.5 medium and Sol 6.1 high. Neither could open this Page (Cursor sign-in), so both worked from the locked vision only. Full reports: mining-game-plan-review under .agents/research on the PC.

Engine Three tracks, one product.

Treat game loop, custom engine, and agent live-change as three parallel tracks. The playable game is the product; the engine experiment and agent contract stay capped and parallel, with an exit gate—if the engine gate fails, keep iterating the disposable prototype.

Agreements (lock these)

Locked

  • + Agents act as a game master through a live scripting engine over a release-only base engine (most of the game is touchable)—not virtual players and not real-time NPC drivers.
  • + Agents propose; the game decides. Validated proposal / plugin inbox; apply at a calm moment; rollback required. No direct live mutation of running simulation state outside that contract.
  • + Plugin architecture over a fixed engine core. Updated after Proto 6: the agent layer grows into full scripting (data, logic, assets) through a validated contract. Not DLL/dylib injection.
  • + Hot-reload tiers: data/plugins first; native rebuild/restart only when the fixed backend changes. No hot-swapping native code.
  • + Game must play offline with no agent. Agents are async/background; authored fallback always works.
  • + One agent contract (CLI + JSON schemas). Do not integrate Claude Code, Codex, and Cursor at once; MCP later as a thin wrapper.
  • + Two-week shape: paper toy → disposable (browser/canvas ok) prototype → vertical slice; engine in a capped parallel track.
  • + Defer: sync/VPN/DB, OpenRouter/GM, combat, galaxy scale, station building, packaging/CI.

Slice decision (locked): both in parallel
